# เปิด Room ใช้งานจริงกับทีม

คู่มือนี้ใช้สำหรับทีมภายในที่ทำงานร่วมกับฟรีแลนซ์และลูกค้า โดยใช้ Vercel เป็นโฮสต์เว็บไซต์, PostgreSQL เป็นฐานข้อมูลถาวร และ Resend ส่งอีเมลยืนยันบัญชี/รีเซ็ตรหัสผ่าน โค้ดและฐานข้อมูล PostgreSQL ทดสอบในสภาพแวดล้อมแยกแล้ว แต่ยังไม่ได้ deploy เว็บไซต์ถาวร เชื่อม Neon จริง หรือส่งอีเมลจริง

## 1. เตรียม Vercel และฐานข้อมูล

Import `CosMD-BBB/Task_Management` จาก GitHub เข้า [Vercel](https://vercel.com/new) แล้วตั้งค่า:

| รายการ | ค่า |
| --- | --- |
| Framework | Vite |
| Node.js | `24.x` |
| Install command | `npm ci` |
| Build command | `npm run build` |
| Output directory | `dist` |
| Production branch | `main` |

ใช้ `vercel.json` ใน repository ซึ่งส่ง `/api/*` ไปฟังก์ชัน API และรองรับหน้าเว็บแบบ SPA ไฟล์ที่มีอยู่ใน `dist/assets` และ `dist/fonts` ได้รับบริการจากระบบไฟล์ก่อนกฎ rewrite

เชื่อม [Neon](https://neon.tech) หรือ PostgreSQL provider ที่รองรับ connection pooling แยกฐานข้อมูลหรือ branch ของฐานข้อมูลสำหรับ **Production** และ **Preview** แล้วผูก `DATABASE_URL` ของ Vercel แต่ละ environment ให้ตรงกัน ห้ามให้ Preview อ่านหรือเขียนฐานข้อมูลทีมจริง

เลือก pooled connection URL ที่เปิด TLS และตรวจ certificate เช่น URL ของ provider ที่ใช้ `sslmode=verify-full` ใช้ CA ตามคำแนะนำของ provider หากจำเป็น และอย่าปิดการตรวจ certificate เลือก region ของฐานข้อมูลและฟังก์ชัน Vercel ให้ใกล้กัน

แอปบน Vercel ต้องมี PostgreSQL และจะปฏิเสธการเริ่มต้นหากไม่มี `DATABASE_URL` SQLite ใช้สำหรับพัฒนาในเครื่องเท่านั้น ข้อมูลใน `.data/workspace.sqlite` **ไม่ได้ย้ายเข้า PostgreSQL อัตโนมัติ** หากต้องเก็บข้อมูลเดิม ให้เตรียมขั้นตอนย้ายข้อมูลและตรวจจำนวน/ความครบถ้วนแยกก่อนเปลี่ยนระบบ

## 2. ตั้งค่า Resend และตัวแปรอย่างปลอดภัย

เพิ่มโดเมน `cosmdskin.com` ใน [Resend](https://resend.com) และตั้ง DNS ตามรายการที่บริการให้ จนสถานะโดเมนผู้ส่งยืนยันเรียบร้อย สร้าง API key สำหรับการส่งอีเมล แล้วใส่ค่าผ่าน **Vercel Environment Variables** เท่านั้น อย่าใส่ค่าลับในโค้ด Git เอกสาร หรือแชต

| ตัวแปร | ค่าที่ต้องตั้ง |
| --- | --- |
| `DATABASE_URL` | pooled PostgreSQL URL ของ environment นั้น พร้อม TLS ตรวจ certificate; เป็นค่าลับ |
| `RESEND_API_KEY` | API key ของ Resend; เป็นค่าลับ |
| `MAIL_FROM` | `Room <info@cosmdskin.com>` หลังยืนยันโดเมนผู้ส่งแล้ว |
| `APP_URL` | HTTPS origin ของเว็บไซต์ เช่น `https://room.example.com` ไม่มี path, query หรือ fragment |
| `SUPERADMIN_EMAIL` | `info@cosmdskin.com` |
| `DATABASE_POOL_MAX` | ไม่จำเป็นต้องตั้ง; ค่าเริ่มต้น `3` ต่อฟังก์ชัน/instance รับจำนวนเต็ม `1`–`10` |

**ห้ามตั้ง `MAIL_MODE=preview` บน Production** ใช้อีเมลจริงสำหรับยืนยันเจ้าของบัญชี โหมด preview เป็นกล่องอีเมลจำลองและอนุญาตบัญชีตัวอย่างเฉพาะระบบทดลองที่แยกไว้

ตั้ง `APP_URL` ของ Production เป็นโดเมนถาวรที่เปิดใช้จริง สำหรับ Preview ที่ทดสอบอีเมลจริง ให้ใช้โดเมนทดสอบที่ตรงกับระบบนั้นและผู้รับทดลองที่ควบคุมได้ เมื่อแก้ Environment Variables ให้ deploy ใหม่เพื่อให้ฟังก์ชันใช้ค่าใหม่

ถ้าทดสอบ Resend จาก Codex Cloud ภายหลัง ต้องอนุญาต `api.resend.com` และผูก secret ไปยังปลายทางนี้ ใช้ proxy และ CA trust ที่ระบบให้ พร้อมเปิด `NODE_USE_ENV_PROXY=1` ตอนเริ่ม Node.js เพื่อให้ `fetch` ใช้ proxy ส่วน Vercel ใช้ค่าลับและเครือข่ายของ Vercel เอง

## 3. ตรวจ migration และการเชื่อมต่อ

เมื่อ API เริ่มครั้งแรก แอปสร้าง/ปรับ schema และข้อมูลเดิมใน transaction เดียว พร้อมบันทึกเวอร์ชันใน `schema_migrations` หาก migration ล้มเหลว การเปลี่ยนแปลงจะ rollback และลองใหม่ได้หลังแก้สาเหตุ เมื่อเวอร์ชันนั้นสำเร็จแล้ว การเริ่ม instance ใหม่จะไม่ไล่เขียนข้อมูลทุกโปรเจกต์อีก

PostgreSQL ใช้ transaction advisory lock เพื่อรองรับการเริ่มหลาย instance และการใช้ transaction pooling การเปลี่ยน schema หรือ migration ในรุ่นต่อไปต้องเพิ่มเวอร์ชันใหม่ในโค้ด กระบวนการนี้ทดสอบกับ PostgreSQL ชั่วคราวจริงแล้ว แต่ยังไม่ได้ทดสอบกับ Neon หรือฐานข้อมูล Production

Pool เริ่มต้นใช้ไม่เกิน 3 connections ต่อ instance; จำนวน instance รวมยังเพิ่มการใช้ connections ได้ ใช้ pooled endpoint และตรวจงบ connections ของ provider ก่อนเพิ่มค่า แอปรอเชื่อมต่อ/รับ connection ไม่เกิน 5 วินาที และกำหนด timeout สำหรับ query/transaction เพื่อลดการค้าง

## 4. เปิดเว็บไซต์และทดสอบด้วยบัญชีจริง

หลัง deploy ให้ตรวจขั้นตอนต่อไปนี้บนโดเมน Production โดยใช้ข้อมูลทดสอบที่ลบได้:

1. เปิดหน้าเว็บและ `GET /api/health`; ต้องได้ `status: "ok"` และ `storage: "postgres"` endpoint นี้รายงานชนิดฐานข้อมูลที่เริ่มต้นไว้ ไม่ได้ทดสอบอ่าน/เขียนฐานข้อมูลใหม่ทุกคำขอ จึงต้องตรวจงานจริงและอีเมลตามขั้นตอนต่อไปด้วย
2. สมัครด้วย `info@cosmdskin.com` ตั้งรหัสผ่านเฉพาะบัญชี และเปิดอีเมลยืนยันที่ส่งจริง บัญชีนี้จะเป็น Super Admin หลังยืนยันสำเร็จ ไม่มีรหัสผ่านกลางหรือบัญชีแอดมินสำเร็จรูป
3. สมัคร/ยืนยันบัญชีอีกสองบัญชี สร้างห้องและงาน เชิญบัญชีหนึ่งเป็น Editor และอีกบัญชีเป็น Viewer ตรวจว่า Editor แก้ไขได้ ส่วน Viewer อ่านได้อย่างเดียว
4. ใช้บัญชีที่ไม่ได้เป็นสมาชิกตรวจว่าเปิดห้อง งาน และความคิดเห็นของห้องนั้นไม่ได้ ทดสอบระงับบัญชีและตรวจว่า session เดิมใช้งานต่อไม่ได้
5. สร้างความคิดเห็นและ @mention ด้วยบัญชีที่แก้ไขได้ ตรวจแจ้งเตือนที่เปิดตรงความคิดเห็น ลองแก้/ลบตามสิทธิ์ และตรวจข้อความหลายบรรทัดบนมือถือ
6. ทดสอบรีเซ็ตรหัสผ่านผ่านอีเมลจริง ลิงก์ต้องใช้ครั้งเดียวและ session เดิมถูกยกเลิก ตรวจว่าลิงก์ใช้ HTTPS origin ที่ตั้งไว้
7. สร้างงานด้วยบัญชีปกติ รีโหลดหน้าเว็บและ deploy ใหม่ แล้วตรวจว่างานเดิมยังอยู่ ทดสอบ List, Board, Calendar และการบันทึกจากสองหน้าต่างพร้อมกัน เมื่อมีงานที่เปลี่ยนไปแล้ว ระบบต้องแจ้งความขัดแย้งแทนการทับข้อมูลเงียบ ๆ
8. ตรวจฟอนต์ รูปโปรเจกต์ และความอ่านง่ายทั้งธีมสว่าง/มืดบน desktop และ mobile ก่อนเชิญทีมเข้าใช้งาน

## 5. จัดสิทธิ์ทีม ฟรีแลนซ์ และลูกค้า

เจ้าของห้องเพิ่มสมาชิกด้วยอีเมลได้เมื่อผู้รับ **สมัครและยืนยันบัญชีแล้ว** ขณะนี้ยังไม่มีอีเมลเชิญแบบ pending สำหรับคนที่ยังไม่สมัคร ให้ผู้รับสมัคร/ยืนยันก่อน แล้วจึงเพิ่มเข้าห้อง

| ผู้ใช้งาน | สิทธิ์ปัจจุบันที่เหมาะสม |
| --- | --- |
| ทีมที่รับผิดชอบงาน | Editor ในห้องที่ต้องทำงาน |
| ฟรีแลนซ์ที่ต้องแก้งานหรือส่งความคิดเห็น | Editor เฉพาะห้องที่เกี่ยวข้อง |
| ลูกค้าที่ดูความคืบหน้าอย่างเดียว | Viewer เฉพาะห้องที่เกี่ยวข้อง |

Viewer **ส่งความคิดเห็น แคปชั่น หรือคำขอแก้ไขไม่ได้** หากลูกค้าต้องให้ feedback โดยไม่แก้งาน ควรเพิ่มสิทธิ์ Commenter/Approver ในงานพัฒนารอบถัดไป การเลือกข้อความประเภท “คำขอแก้ไข” ปัจจุบันไม่ได้เป็นระบบอนุมัติที่มีขั้นตอนและสิทธิ์เฉพาะ

ลำดับพัฒนาต่อที่ช่วยงานร่วมกับคนนอกทีมมากที่สุดคือ สิทธิ์ Commenter/Approver, อีเมลเชิญที่รับได้หลังสมัคร, ประวัติการเปลี่ยนงาน และ Undo/ถังขยะสำหรับกู้รายการที่ลบ ปัจจุบันมี audit log สำหรับการจัดการบัญชีโดยแอดมินแล้ว แต่ยังไม่มีประวัติการเปลี่ยนงานที่ใช้ดูย้อนหลังหรือกู้ค่าก่อนแก้ ส่วนไฟล์แนบปัจจุบันเป็นลิงก์; ผู้รับยังต้องมีสิทธิ์ที่ Google Drive/Figma หรือบริการต้นทาง

## 6. สำรองข้อมูลและดูแลระบบ

เปิด backup และ point-in-time recovery (PITR) ตามแพ็กเกจ PostgreSQL ที่ใช้ กำหนดความถี่และระยะเก็บให้ตรงกับข้อมูลทีม ก่อนเปิดใช้จริงให้กู้สำเนาไปฐานข้อมูลทดสอบที่แยกจาก Production แล้วตรวจบัญชี โปรเจกต์ งาน ความคิดเห็น และสิทธิ์ บันทึกวิธีกู้คืนและผู้รับผิดชอบ; การมีปุ่ม backup อย่างเดียวไม่ยืนยันว่ากู้ระบบกลับมาได้

ติดตาม Vercel function errors/latency, จำนวน database connections, พื้นที่ฐานข้อมูล และผลส่งอีเมลใน Resend ตั้งการแจ้งเตือนเมื่อ API เกิด 5xx ต่อเนื่องหรือส่งอีเมลล้มเหลว โดยไม่บันทึก token, connection URL, รหัสผ่าน หรือเนื้อหาอีเมลของสมาชิกลง log

Rate limiter ปัจจุบันอยู่ในหน่วยความจำของแต่ละ instance จึงไม่ใช่ขีดจำกัดรวมข้าม serverless instances ก่อนเปิดรับผู้ใช้จำนวนมากหรือเปิดสมัครสาธารณะวงกว้าง ให้เพิ่ม distributed rate limiting หรือกฎ Vercel WAF สำหรับ signup/login/reset และตรวจผลจริง การทดสอบรอบนี้ยังไม่ได้วัดโหลดหรือจำนวนผู้ใช้สูงสุด

Manrope ฝังในเว็บแล้ว แต่ไฟล์ **Sukhumvit Thai / Sukhumvit Set ของจริงยังไม่มีใน cloud checkout** ต้องนำไฟล์แบรนด์ที่มีสิทธิ์ใช้งานมาเพิ่มและตรวจฟอนต์ที่ render จริงก่อนอ้างว่าภาษาไทยตรงกันทุกอุปกรณ์ อย่านำฟอนต์อื่นมาเปลี่ยนชื่อแทน ดู [แหล่งที่มาและไฟล์ที่ขาด](../public/fonts/README.md)

## Codex Cloud กับเว็บไซต์จริง

การ **Save/Publish environment ใน Codex** บันทึก configuration และสภาพแวดล้อมสำหรับพัฒนา ไม่ได้สร้างเว็บไซต์ Vercel หรือ deploy ฐานข้อมูล/อีเมลให้เสร็จ ต้องเชื่อมบริการและตรวจ deployment ตามขั้นตอนข้างต้น

เมื่อผู้มีสิทธิ์เชื่อม GitHub repository กับ Vercel แล้ว การให้ ChatGPT/Codex แก้โค้ด ทดสอบ และ push commit ไป branch Production จะเริ่ม deployment อัตโนมัติตามการตั้งค่า Vercel ส่วน branch อื่นสร้าง Preview ตามการตั้งค่า การแก้โค้ดในแชตหรือใน workspace ที่ยังไม่ push จะยังไม่เปลี่ยนเว็บไซต์ที่ทีมใช้อยู่
